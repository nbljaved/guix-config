* Read this first
** What this does
It wipes the T460's whole disk and installs Debian 13 "trixie" with full-disk encryption (LUKS), and with hibernation rather than Secure Boot ([[*D7 — Secure Boot or hibernation][D7]]). It then installs Guix on top from a *patched* CI tarball. After that:

- *Debian owns* anything that runs as root or checks a password: kernel, firmware, bootloader, X server, =i3lock=, NetworkManager, PipeWire, Bluetooth and Tailscale. Security fixes arrive through =unattended-upgrades=.
- *Guix owns* your user environment: StumpWM, Emacs, kitty, and the shared =current-profile-manifest= plus =thinkpad-manifest.scm=.

** The one rule behind the design
The Guix daemon runs *unprivileged* here, as the =guix-daemon= user (see [[*D1 — Guix daemon mode][D1]]). It owns =/gnu/store=, so if it were ever compromised, the attacker could alter anything in the store. On Debian that means your Guix *apps*, not the OS, as long as *root never runs a store binary*. The one exception you can't avoid is =sudo -i guix pull=, which is how the daemon gets updated.

That is why =tailscaled=, =i3lock=, the X server and the rest of the root-side software come from apt, not Guix.

* Decisions to make before starting
** D1 — Guix daemon mode
- *Unprivileged (recommended; the installer's default on Debian).* This differs from the pc's D1 on purpose:
  - On Guix System the store /is/ the OS, so a daemon that owns the store is effectively root anyway.
  - On Debian the OS lives outside the store, so the rule above keeps a daemon compromise at user level.
  - Cost: local builds may fail their test suites (=chown= returns EINVAL; see the pc runbook's D1). With substitutes, local builds are rare here. =nbl-emacs= is the main one.
- Privileged would mean hand-editing the systemd unit and creating =guixbuild= users. It's not covered here.

** D2 — Where Tailscale comes from
- *Tailscale's apt repo (recommended).* It's signed, and [[*7.1 Tailscale][7.1]] adds it to =unattended-upgrades=, so patches arrive automatically. You trust Tailscale's builds.
- Your Guix source build keeps the build under your control. But =tailscaled= would then run as root from the store, which breaks the rule, and it only gets patched when you rebuild.

** D3 — How X starts
- *=startx= on tty1, no display manager (recommended).* It means fewer root components. Your login shell sources =/etc/profile.d/zzz-guix.sh=, so StumpWM starts with the full Guix environment, and X runs rootless through logind.
- A display manager such as lightdm needs extra work to get Guix's environment into the session. It's not covered here.

** D4 — SSH server on the laptop
- *No (recommended).*
- Yes: tick "SSH server" in [[*3.4 Software selection][3.4]]. The firewall then allows it only over the tailnet ([[*7.1 Tailscale][7.1]]).

** D5 — GitHub SSH key
- *A new key for this machine (recommended).* If the laptop is lost, you revoke just that key.
- Restoring the T460's old key also works, but then remove the old one from GitHub later anyway.
- =~/.age/key=: copy it over only if you need to decrypt age files on the laptop.

** D6 — Nix
- *Skip for now (recommended).* On Debian, =uv=, prebuilt wheels and vendor binaries run natively, which removes most of the reasons you use Nix on the pc.
- Debian packages Nix 2.26 (=nix-setup-systemd=) if you miss it later. That's not covered here.

** D7 — Secure Boot or hibernation
You can't have both. Debian's kernel enters "lockdown" when Secure Boot is on, and lockdown disables hibernation and resume (see [[*D. Facts and sources (checked 2026-09-21)][Facts]]).
- *Hibernation, with Secure Boot off (chosen 2026-10-03).* What you want protected is the data on the disk, and LUKS is what protects it. Hibernation writes RAM into the encrypted swap and powers the machine off, so the keys leave memory and the passphrase is asked again on resume. Suspend instead keeps the keys in RAM, which is the weaker state to leave a laptop in.
- *Secure Boot, with no hibernation.* It would stop a root-level compromise from installing a bootloader or kernel that survives a reinstall, and it blocks unsigned kernel modules, =kexec= of unsigned kernels and userspace access to physical memory. It would *not* protect your data: =/boot= is unencrypted and the initrd that asks for the passphrase is unsigned, so boot-time tampering stays possible either way. Closing that needs TPM-measured boot, which this plan doesn't set up.
- So the cost of this choice is that bootkit protection and kernel lockdown. The gain, besides hibernation, is that [[*4.2 Firmware updates (fwupd)][4.2]] drops the whole Microsoft-CA-expiry problem.
- To change your mind later: enable Secure Boot in BIOS setup, do the CA work described in 4.2, and expect =systemctl hibernate= to stop working.

- *No backup drive (chosen 2026-10-04).* The bet is that everything you need is in a GitHub repo. [[*F. ** TODO 4.7 Hibernation (D7)
This is what [[*D7 — Secure Boot or hibernation][D7]] traded Secure Boot for, so it's worth getting working. Hibernation needs swap at least as big as your RAM, and the installer's swap is smaller. Grow it into the room 3.3 left:
#+begin_src sh
free -h; cat /proc/swaps                         # swap size against RAM (1.1)
sudo vgs                                         # VFree: what 3.3 left spare
sudo lvs -o lv_path,lv_size,lv_name              # the swap volume's own path, e.g. /dev/thinkpad-vg/swap_1
SWAP=/dev/<vg>/<swap lv>                         # <- fill in from that line; not the /dev/mapper name
SIZE=$(awk '/MemTotal/ {printf "%dG", int($2/1048576)+2}' /proc/meminfo); echo "$SIZE"   # RAM rounded down, +2
sudo swapoff "$SWAP"
sudo lvextend -L "$SIZE" "$SWAP"                 # absolute size, and it must fit VFree
sudo mkswap "$SWAP"
sudo swapon "$SWAP"; sudo swapon --show
#+end_src
=mkswap= gives the volume's *contents* a new UUID. The volume's path doesn't change. So look at how the two files that name the swap refer to it:
#+begin_src sh
sudo blkid -s UUID -o value "$SWAP"              # the new UUID
cat /etc/initramfs-tools/conf.d/resume
grep -i swap /etc/fstab
#+end_src
- *By path* — =RESUME=/dev/mapper/thinkpad--vg-swap_1= and an =/dev/mapper/…= line in =fstab=. That's what Debian's guided LVM writes, and *there is nothing to edit*: the path survived =mkswap=.
- *By UUID* — either file says =UUID===. Then it is now stale, and the machine would boot a fresh session instead of resuming. Put the UUID printed above into it:
  #+begin_src sh
  sudoedit /etc/initramfs-tools/conf.d/resume    # RESUME=UUID=<the new UUID>
  sudoedit /etc/fstab                            # the swap line's UUID=
  #+end_src
- Either way, rebuild the initramfs, since =/etc/initramfs-tools/conf.d/= is copied into it:
  #+begin_src sh

  #+end_src
Then test it, with nothing unsaved open:
#+begin_src sh
sudo systemctl hibernate
#+end_src

- "Not enough swap space for hibernation" means the =lvextend= wasn't big enough.
- If 3.3 used the whole volume group after all, =lvextend= has no room. Either redo the install, or use a swap *file* on the encrypted root with =resume_offset=, as in =REINSTALL-pc.org= step 2.7.

** B. Troubleshooting
- *=F12= lists the stick, but choosing it does nothing*: the ISO went to a partition (=/dev/sdb1=) instead of the device (=/dev/sdb=), so the firmware sees the stick's old partition table and no EFI loader. =lsblk -o NAME,FSTYPE,SIZE,LABEL /dev/sdb= shows the giveaway: =iso9660= sitting on =sdb1= at the stick's full size. Rewrite it as in 2.2.
- *=F12= lists old entries such as =grub= or =artix= that do nothing*: stale UEFI boot entries in NVRAM from earlier installs, pointing at files that no longer exist. Harmless. After the install, =sudo efibootmgr -v= lists them and =sudo efibootmgr -b <NN> -B= deletes one.
- *=systemctl hibernate= fails with "Not enough swap space"*: swap is smaller than RAM. Grow it as in [[*4.7 Hibernation (D7)][4.7]].
- *The machine boots a fresh session instead of resuming*: =/etc/initramfs-tools/conf.d/resume= points at the wrong swap. If it names a =UUID=, that UUID went stale when 4.7 ran =mkswap=; if it names a =/dev/mapper/…= path, check the path still exists. Fix it, then =sudo update-initramfs -u -k all=.
- *=systemctl hibernate= says the operation isn't supported*: Secure Boot is on, which locks the kernel down. Turn it off in BIOS setup (3.1, D7).
- *The USB stick or network boot won't start when Secure Boot is on* ("Security violation" / "verification failed"): the firmware's db lacks a CA the shim needs. Turn Secure Boot off, install, do 4.2 (=fwupd= adds the 2023 CA), turn it back on, and confirm with =mokutil --sb-state=.
- *=guix-install.sh= says "Missing commands: newgidmap"*: run =sudo apt install uidmap=.
- *The daemon runs as =root=*: the installer took the privileged path. Either the unit had no =User=guix-daemon= (wrong tarball), or systemd wasn't detected. Uninstall and redo 5.1–5.2.
- *AppArmor blocks builds*: =sudo journalctl -k | grep 'apparmor="DENIED".*guix'=. Report it upstream. As a last resort, run =sudo apt install apparmor-utils && sudo aa-complain guix-daemon=.
- *A local build fails with =chown= / =OSError: [Errno 22] Invalid argument=*: that's the unprivileged daemon (D1). Wait for a substitute, build it on the pc (only once the pc is reinstalled), or for your own packages use =--without-tests=<package>=.
- *Locale warnings in Guix apps*: =glibc-locales= is in the manifest. Open a new login shell so =GUIX_LOCPATH= is set.
- *Guix apps can't find fonts*: run =fc-cache -f=.
- *blueman or udiskie only half work*: they need system D-Bus services that a Guix profile can't register, and your Guix profile shadows =/usr/bin= in =PATH=. 4.5 installs Debian's =blueman= and 6.6 calls it by absolute path; =type -a blueman-applet= shows which copy you'd get. For =udiskie=, =udisks2= from 4.5 is what matters; if it still misbehaves, =sudo apt install udiskie= and call =/usr/bin/udiskie= the same way.
- *StumpWM doesn't start after a tty1 login*: =hostname= must print =thinkpad=. Check the =.bash_profile= block from 6.6.
- *=make apply-guix-profile= skips =thinkpad-manifest.scm=*: =hostname= must be =thinkpad=, and =/etc/os-release= must not contain =ID=guix=.
- *No Wi-Fi after 4.6*: =nmcli device= shows "unmanaged" if =/etc/network/interfaces= still lists the device.
- *Network boot: =dnsmasq= logs nothing*: on the pc, =ip -br link= must show the Ethernet port =UP= with =LOWER_UP=, which means the cable is seated at both ends. On the T460, /UEFI IPv4 Network Stack/ must be on. If it tries IPv6 first, wait for that to time out.
- *Network boot: =DHCPACK=, but no =sent= lines*: something on the pc blocks TFTP (UDP port 69). =sudo "$IPT" -S INPUT= should show =-P INPUT ACCEPT=, which is the pc's default.
- *Network boot: GRUB can't find =/debian-installer/amd64/linux=*: =--tftp-root= must be the directory that contains =debian-installer/= (E.2).
- *Route P: the installer can't reach the mirror*: on the pc, =sysctl net.ipv4.ip_forward= must print =1=, and =sudo "$IPT" -S FORWARD= and =sudo "$IPT" -t nat -S POSTROUTING= must show the E.4 rules. Check that the pc itself is online.

** E. Network boot instead of a USB stick
This replaces the USB stick in Phase 2 and 3.1. Nothing else changes. The pc side works before or after the pc reinstall, because it never asks =guix= to download anything (E.0).
#+begin_example
   internet
      │ Wi-Fi
┌─────┴──────────────┐  Ethernet cable  ┌─────────────┐
│ pc   10.99.0.1     │──────────────────│ T460        │
│ dnsmasq: address,  │  only these two  │ 10.99.0.5x  │
│ boot files, DNS    │  machines on it  │             │
└────────────────────┘                  └─────────────┘
#+end_example
- *How it works:* at =F12= → network, the T460's firmware asks the network for an address and a boot file. =dnsmasq= on the pc answers, then serves Debian's netboot files over TFTP.
- *Why E.1 and the direct cable matter:* with Secure Boot off (D7), the firmware checks none of these files, and TFTP has no authentication either. So the pc verifies the image before serving it, and nothing else is on the cable to swap it. (Even with Secure Boot on, shim, GRUB and the kernel are checked but the initrd is not.)
- The installer runs from RAM, so it can still wipe the whole disk. It downloads its packages from Debian, so the T460 needs internet. Pick a route:
  - *Route R, your router is within reach (recommended).* The pc only serves the boot. Once the installer's first screen is up, move the cable from the pc to the router. Skip E.4: the pc never forwards traffic.
